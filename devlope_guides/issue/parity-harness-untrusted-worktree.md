# [Gate 4｜新增錯誤風險] Parity harness requires an external trusted-worktree approval

## Status

Resolved with caveat. The harness now rejects worktrees without an external
approval manifest. Full OS-level sandboxing remains a separate hardening option
for any future workflow that must execute arbitrary PR worktrees.

## Priority

High

## Category

Security

## Review gate

Gate 4

## Issue source and ownership

- Source: Gate 4 review finding.
- Ownership: Parity harness execution boundary.
- Scope: CI and review workflows that run the parity harness.

## Evidence

The parity harness uses a child process to import candidate TypeScript modules.
The child process receives only a minimal environment and a timeout, and it is
started only after the trusted parent validates an approval manifest located
outside the candidate worktree.

The harness imports these candidate modules:

- [`src/core/env.ts`](../../src/core/env.ts)
- [`src/deposit/presets.ts`](../../src/deposit/presets.ts)

The harness resolves and canonicalizes the worktree path.

The approval manifest records the canonical worktree path, HEAD commit, and
input checksums.

The harness rejects an approval file or output directory inside either
candidate worktree.

Relevant code:

- [`scripts/deposit-presets-parity.ts:212`](../../scripts/deposit-presets-parity.ts:212)
- [`scripts/deposit-presets-parity.ts:377`](../../scripts/deposit-presets-parity.ts:377)
- [`scripts/deposit-presets-parity.ts:678`](../../scripts/deposit-presets-parity.ts:678)

## Problem

The import operation still executes candidate code with the OS permissions of
the child process. The approval manifest is therefore the trust boundary: the
current harness is not a sandbox for arbitrary PR code.

The parent process does not import candidate modules. It launches the child
only after the approval manifest matches the exact worktree, commit, and input
checksums. The child does not inherit CI secrets from the parent environment.

## Impact and trigger

An intentionally approved worktree can still access files and network services
available to the child process. This is accepted only for trusted checkouts;
the harness now rejects an arbitrary worktree before candidate loading.

The child environment is reduced to `PATH` and Git safety variables, and the
candidate execution has a timeout. The worktree is checked again after output
publication and after the complete comparison.

## Resolution boundary

The current implementation uses the approved-checkout control rather than a
container or OS sandbox. This keeps the parity workflow usable without adding a
runtime dependency on Docker, while enforcing the restriction in the harness.

The approval manifest is generated by a trusted caller outside the candidate
worktree and is matched against the canonical path, HEAD, and input checksums.

The current harness rejects a run without a matching trusted-checkout approval.

This issue does not change deposit business logic or the current runtime API.

Arbitrary PR worktrees remain outside the supported execution boundary.

## Enforced restriction

Use only an approved and verified checkout with the current harness. The
approval file must be created outside the candidate worktree by a trusted
caller and must match the exact worktree path, HEAD, `.env.test` checksum, and
`data/deposit` checksum.

Do not run the current harness with an arbitrary PR worktree.

The harness rejects a run without this manifest and rejects output written into
either candidate worktree.

## Future hardening

The approved-checkout control is implemented. A future arbitrary-PR workflow
must run candidate code in a disposable Docker container or stronger sandbox.

For the isolated execution environment:

- Run the candidate loader inside the container or sandbox.
- Keep the trusted comparison outside the candidate environment.
- Return only defined preset data, such as JSON.
- Do not pass CI secrets to the candidate.
- Allow no network access.
- Mount the worktree as read-only.
- Use a trusted image with a pinned digest.
- Use a non-root user.
- Drop all unnecessary capabilities.
- Do not use privileged mode.
- Do not mount the Docker socket.
- Limit CPU, memory, process count, and execution time.

The trusted harness must not import candidate code in its own process.

Docker shares the host kernel.

Use a stronger sandbox or an isolated runner for a high-threat environment.

## Acceptance criteria

- The trusted parent process does not import candidate code.
- An external approval manifest matches the canonical worktree path, commit,
  and input checksums.
- Runs without an approval manifest are rejected.
- Candidate output is written outside the worktree.
- Candidate execution receives no inherited CI secret variables and has a
  timeout.
- The documentation defines the accepted checkout sources and approval step.
- Tests cover missing approval and worktree/output boundary violations.

## Risk → Test → Test layer

| Risk | Test | Test layer |
| --- | --- | --- |
| Candidate code can access CI credentials | Run a candidate fixture without injected credentials and verify that no credentials are available | Security integration |
| Candidate code can access network services | Run a candidate fixture that attempts a network request and verify that the request fails | Security integration |
| Candidate code can access host files | Run a candidate fixture in the isolated environment and verify the allowed mount boundary | Security integration |
| The trusted process can import candidate code | Test the process boundary and verify that the trusted harness reads only the defined output | Harness integration |
| An arbitrary worktree can bypass the trust rule | Test checkout validation with approved, modified, and unapproved worktrees | Harness unit |

## Future verification

After implementation, run the verification gates that match the changed files.

- Run `bun run test:api`.
- Run `tsc --noEmit`.
- Create an approval manifest with `--create-approval` from a trusted caller.
- Run the parity harness with the matching approval file(s).
- Confirm that missing or mismatched approval is rejected before candidate loading.
- Confirm that output directories inside candidate worktrees are rejected.
- If arbitrary PR support is added later, run the sandbox security tests for
  secrets, network, host files, and resource limits.

## Residual risk

The harness still runs an intentionally approved candidate with ordinary child
process OS permissions; the approval manifest is not a substitute for a
container or stronger sandbox. Do not approve arbitrary PR worktrees. Reopen
this issue before enabling arbitrary worktree execution in CI.
