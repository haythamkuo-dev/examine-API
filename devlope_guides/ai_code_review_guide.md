# Code Review 指引

本文件只負責 branch、diff、PR 與程式碼審核的流程、Gate 分析、issue 處理、輸出與紀錄。專案架構、測試工具、驗證命令與完成條件依 `AGENTS.md`；本指南在 Review 中引用這些規範，不另立或覆寫專案級規範。AI 必須檢查目前分支的實際變更，並判斷實作目標、完成度、行為影響和風險。AI 使用 Gate Review 或 PR Reviewer 全域審核揭露 issue，並引導開發者處理。

本文件定義兩種 Review 模式：Gate Review 和 PR Reviewer 全域審核。

Gate Review 依序完成七個 Gate。PR Reviewer 全域審核分成兩個階段。第一階段依 Gate 1 至 Gate 6 完成靜態分析。第二階段依 Gate 7 執行本機單元測試。全域審核不使用 Gate 狀態，但仍須完成 Gate 1 至 Gate 6 的所有必分析項目和第三章所有適用的選擇分析項目。Reviewer 必須為每項 issue 標記主要 Gate 分類。

## 一、Review Gate 描述

Review Gate 用於分支合併前的檢查。Gate 涵蓋實作目標、業務邏輯、runtime 風險、新增錯誤風險、架構、重要資料持久化和本機單元測試。

第 1.1 至 1.6 節適用於 Gate Review，但第 1.3 節也定義如何切換到 PR Reviewer 全域審核。第 1.7 節同時適用於兩種模式。

### 1.1 Review 起點

AI 必須比較目標分支與預定合併基準的實際變更，並以此開始 Review。AI 必須記錄 base 和 head 的 ref 與 commit。Gate 1 的目標來源、輸出方式和開發者確認方式依第 2.1 節執行。

### 1.2 靜態與動態驗證邊界

Gate 1 至 Gate 6 只進行程式碼、diff、規格和文件的靜態分析。不得執行 build、單元測試、整合測試、E2E 或其他 runtime 驗證。AI 可以閱讀測試程式和既有測試結果，但不得用測試執行結果取代程式碼與文件分析。

`tsc --noEmit` 屬於靜態型別分析。若 `AGENTS.md` 依變更範圍要求執行，應在 Gate 1 至 Gate 6 階段完成並記錄；不得將其視為 build 或 Gate 7 的單元測試，也不得以型別檢查結果取代 Gate 7 測試。

Gate Review 只有在 Gate 1 至 Gate 6 都是 `PASS` 或有充分理由的 `N/A` 後，才能進入 Gate 7。

PR Reviewer 全域審核只有在完成 Gate 1 至 Gate 6 的靜態分析和 issue 處理後，才能進入 Gate 7。Gate 7 的測試結果只提供動態證據。測試結果不得取代前六個 Gate 的分析結論。

### 1.3 Issue 發現後的互動與處理

AI 必須先完成每個 Gate 的分析，再依第 1.6 節輸出結果。Gate 1 第一階段和 Gate 2 的開發者確認，分別依第 2.1 節和第 2.2 節執行。

Gate 1 第二階段或 Gate 3 至 Gate 6 發現 issue 時，AI 必須將 Gate 標記為 `ISSUE_FOUND`。接著，AI 必須逐項引導開發者處理 issue，或依第 1.7 節執行人工終止。互動時可以補充必要證據和解決方式。最終 Review 文件只保留本節和第 1.7 節要求的最新結果。切換到 PR Reviewer 全域審核後，由 PR 平台保存問題和處理紀錄。

Gate Review 依下列第 1 至第 3 項及第 5 項處理 issue，並記錄結果。開發者選擇轉入 PR Reviewer 全域審核後，改依第 4 項執行：

1. `Issue 告知與行動引導`
   - AI 必須逐項說明 issue 的原始問題、判斷依據、主要影響和解決方向。AI 也必須說明開發者下一步要採取的行動。AI 不得只提出問題，還必須協助開發者收斂處理方式。
   - 同一 Gate 發現多項 issue 時，AI 必須先依第 1.7 節完成分析和排序。接著，AI 必須編號列出目前最高優先級的所有 issue，並分別請開發者選擇直接修正或提出論證。AI 不得用一次概括確認合併不同問題。開發者也可以依第 1.7 節人工終止目前的 Gate，或停止 Gate Review 並切換到 PR Reviewer 全域審核。
   - 任一 issue 尚未處理完畢時，Gate 必須維持 `ISSUE_FOUND`。Gate 不得進入下一關。若沒有執行人工終止，所有 issue 都處理完畢後，Gate 才能判定為 `PASS`。
   - AI 可以提出具體修正方案。Review 期間，AI 只能新增或修改本次唯一的 `devlope_guides/review/**` Review 文件。AI 不得修改程式碼、`devlope_guides/issue/**` 或其他文件。若開發者要 AI 實作修正，必須先暫停 Review，並明確授權實作範圍。
2. `直接修正`
   - 開發者可以自行修正 issue。若要 AI 修正，開發者必須先暫停 Review，並明確授權 AI 按雙方確認的範圍實作。
   - 修正完成並恢復 Review 後，AI 必須重新執行發現問題的 Gate。若 Gate 1 第二階段的修正同時改變目標，AI 必須先回到第一階段，重新取得開發者確認。
   - AI 重新分析並確認某項 issue 已消除後，才能將該 issue 標記為已處理。同一 Gate 的其他 issue 也必須已修正或經論證允許通過，Gate 才能改判為 `PASS`。
   - 最終 Review 文件只記錄 Gate 的最新狀態和本節要求保留的 issue。文件不得保留已解決的 issue、修正過程或互動紀錄。AI 未重新分析確認，或重新分析後 issue 仍然成立時，不得標記為已解決。
3. `開發者論證`
   - 開發者可以選擇不修正 issue，並主張不採納或延後處理。開發者必須提出具體理由和證據。不採納時，開發者必須說明 AI 的判斷為何不成立或不適用。延後處理時，開發者必須說明影響範圍、發生條件、接受風險的理由、現有防護和後續處理方式。
   - AI 必須協助釐清雙方的判斷差異。AI 必須引導開發者說明理由，核對相關程式或文件證據，並指出尚未回答的風險。除第 1.7 節的人工終止外，AI 不得替開發者編造通過理由。AI 也不得只因開發者宣告接受風險，就結束 Review。
   - 開發者決定是否接受殘餘風險。AI 依據證據判斷論證是否足以讓 Gate 通過。
   - 若證據顯示原始問題不成立或不適用，AI 將 issue 判定為「不採納」。若 issue 仍然成立，但開發者明確接受殘餘風險、提出足以支持安全延後的論證，並依第 1.4 節建立追蹤，AI 可以將 issue 判定為「延後處理」。
   - 若開發者未明確接受殘餘風險，或證據不足以支持安全延後，issue 維持未處理，Gate 維持 `ISSUE_FOUND`。開發者必須修正 issue 並重新分析，或依第 1.7 節執行人工終止。人工終止不要求逐項論證。
4. `轉入 PR Reviewer 全域審核`
   - 開發者可以停止目前的 Gate Review，並要求 PR Reviewer 全面審查分支。切換後，Reviewer 不沿用現有 Gate 狀態，也不必逐 Gate 輸出或在發現 issue 時停止分析。Reviewer 仍須遵守第 1.2 節的驗證界線。此模式仍使用 Gate 編號作為分析框架和 issue 分類。
   - PR Reviewer 必須依第二章的 Gate 1 至 Gate 6 完成全面靜態分析，也必須判斷第三章各選擇分析項目是否適用。Reviewer 可以依風險調整順序，也可以跨 Gate 整合呼叫鏈、資料流和既有驗證證據。
   - PR Reviewer 不必把輸出拆成六個 Gate，不必產生 Gate 狀態，也不必為不適用項目輸出 `N/A`。但 Reviewer 必須檢查完整分支。Reviewer 不得因發現第一項 issue 或收到人工終止要求而停止剩餘靜態分析。依第 1.7 節完成人工終止時，Reviewer 只停止輸出和處理終止點以下的 issue。
   - 靜態分析完成後，review summary 必須確認已完成 Gate 1 至 Gate 6 和所有適用的選擇分析項目。
   - Reviewer 完成 Gate 1 至 Gate 6 的靜態分析和 issue 處理後，才能依 Gate 7 執行本機單元測試。Gate 7 只補充動態證據，不得取代或改寫前六個 Gate 的分析結論。
   - 每項成立的 issue 都必須在標題或描述開頭標記主要 Gate，格式為 `[Gate N｜<Gate 名稱>]`。Issue 涉及多個 Gate 時，選擇最直接違反的判斷基準作為主要 Gate，並在依據中說明其他相關 Gate。不得為多重分類重複建立同一項 issue。
   - Gate 2 辨識出的既有業務邏輯變動本身不是 issue。若變動也顯示目標不一致或實際風險，則將該問題歸入 Gate 1 或最相關的 Gate 3 至 Gate 6。Gate 7 發現的測試 issue 歸入 Gate 7。
   - Issue 可定位到特定程式碼時，使用 inline comment。跨檔案或整體流程問題使用 review summary。每項 issue 都必須包含完整的問題描述、判斷依據、主要影響和解決方向，讓開發者可以採取行動。
   - PR Reviewer 只審查，不得修改受審分支。若 issue 實質影響分支目標、正確性、安全性、可維護性或必要驗證，使用 `REQUEST_CHANGES`。其他 finding 使用一般 comment。
   - 開發者修正或回覆後，Reviewer 必須重新檢查。Reviewer 必須執行 Gate 7，且確認本分支沒有引入測試失敗。若沒有適用的本機單元測試，Reviewer 必須明確記錄。只有 Gate 1 至 Gate 6 沒有未處理的 blocking issue，且 Gate 7 已完成時，Reviewer 才能使用 `APPROVE`。
5. `論證結果紀錄`
   - 開發者論證後未直接修正的 issue，最終 Review 文件必須保留 AI 的原始問題描述和一句結論。格式為 `<原始問題> — <不採納／延後處理／未處理>：<主要依據>`。若延後處理，結論也必須寫出殘餘風險和追蹤文件連結。
   - Gate 因任一 issue 尚未完成處理而維持 `ISSUE_FOUND` 時，其他尚未處理的 issue 只保留原始問題描述並標示「未處理」，不得替尚未進行的論證撰寫結論。
   - Review 文件不得保存逐輪對話或完整辯論過程。AI 必須將雙方論點收斂成可獨立理解的結論，不得以互動逐字稿取代判定結果。

`BLOCKED` 不適用直接修正、開發者論證或人工終止。AI 判定為 `BLOCKED` 時，必須先補足資訊或環境，或解決造成阻塞的不一致。之後，AI 必須重新分析。不得用開發者論證或人工終止將 `BLOCKED` 改判為 `PASS`。

### 1.4 Gate 判定狀態與 Issue 歸屬

Gate 使用以下狀態：

1. `PASS`：Gate 1 第二階段或 Gate 3 至 Gate 6 沒有未處理的 issue。已修正或經論證允許通過的 issue 視為已處理。若較高優先級 issue 已形成允許通過的結果，其餘 issue 可以依第 1.7 節人工終止。Gate 2 必須完成開發者確認。Gate 7 必須完成必要測試，且不得有本分支引入的測試失敗。
2. `ISSUE_FOUND`：Gate 1 第二階段或 Gate 3 至 Gate 6 有尚未處理的 issue，或 Gate 7 發現本分支引入的測試失敗。此狀態不得改判為 `PASS`。Gate Review 不得進入下一關或宣告通過。
3. `BLOCKED`：比較基準、規格、文件、程式碼或環境資訊不足，導致 AI 無法判定；或 Gate 1、Gate 2 重新分析後仍無法取得一致理解。分支不得進入下一關。
4. `N/A`：該 Gate 不適用於本次分支。AI 必須記錄原因。不得用 `N/A` 代替尚未完成的分析。

Gate 1 不得判定為 `N/A`。其他 Gate 只有在完成適用性檢查後才能判定為 `N/A`。

AI 提出 issue 後，必須先比較 base 與目前分支。AI 必須判斷問題是專案既有 issue，還是分支獨有 issue，並在第 1.3 節的解決方向和開發者論證中說明歸屬。判準如下：

1. `專案既有 issue`：問題在 base 已經存在，且當前分支沒有新增、擴大或提高其發生機率與影響。
2. `分支獨有 issue`：問題由當前 diff 引入、擴大或暴露成為目前實作目標的必要風險。

若分支依賴既有 issue 才能運作，或使既有 issue 的影響加重，AI 必須將它列為本分支要處理的 issue。不得只以「專案既有」為由排除。

對專案既有 issue，AI 必須判斷修正是否屬於本次目標，以及是否會擴大分支範圍。若 issue 不影響本分支目標，而修正會增加模組、業務決策或大量 diff，則不得將修正納入本 PR。

開發者必須建立 `devlope_guides/issue/<issue-slug>.md` 追蹤文件。AI 必須在 Review 文件中連結該議題，並依第 1.3 節完成開發者論證。

本分支原則上必須修正分支獨有 issue。若修正會大幅增加 PR 複雜度或需要額外業務決策，開發者可以主張延後處理。此時，第 1.3 節的論證必須依序回答：

1. Issue 是否影響既有或新增業務邏輯的正確性。
2. Issue 的實際影響範圍、發生條件、嚴重度與風險是否可接受。
3. Issue 是否能在不破壞本次實作目標的前提下延後處理。
4. 延後期間是否具有足夠的既有防護、監控或限制條件。

每項延後處理的 issue 都必須有追蹤文件。開發者必須在 `devlope_guides/issue/<issue-slug>.md` 記錄 issue 來源、歸屬、程式或文件證據、影響範圍、本 PR 不處理的原因、已接受的殘餘風險和後續修正方向。追蹤文件不能取代第 1.3 節要求的風險論證。

### 1.5 執行順序與結論

本節只規定 Gate Review 的順序。切換到 PR Reviewer 全域審核後，不適用本節。

Gate Review 必須依 Gate 編號順序執行。前一個 Gate 必須判定為 `PASS` 或有充分理由的 `N/A`，才能進入下一關。`ISSUE_FOUND` 必須依第 1.3 節逐項處理，或在符合第 1.7 節條件時由開發者人工終止。`BLOCKED` 必須停止流程，直到補足資訊。Gate 7 也必須遵守第 1.2 節的條件。

最終結論只記錄以下事項：Review 是否通過、未處理的 blocking finding、人工終止範圍，以及尚未執行的驗證。不要重複各 Gate 已保存的內容。

所有適用 Gate 都是 `PASS`，且沒有未處理或未被人工終止涵蓋的 blocking finding 時，分支才能通過 Review。完整紀錄依第 1.6 節撰寫。

### 1.6 Review 輸出、撰寫與保存

Review 輸出只呈現各 Gate 的核心結果，不重複 AI 的完整分析。

本節格式適用於逐 Gate 對話和最終 Review 文件。逐 Gate 對話發現 issue 時，AI 還必須依第 1.3 節提供解決方向和下一步行動。最終 Review 文件只保留第 1.3 節和第 1.7 節要求的最新結果。

1. Gate 1 第一階段輸出 `目標清單`。每項目標必須依第 2.1 節說明問題、預期行為和完成條件。開發者確認前，不記錄 Gate 結果。開發者確認後，記錄確認結果，再進入第二階段。
   - 第二階段逐項檢查目標是否完成，以及變更是否超出目標。沒有 issue 時，只輸出 `Gate 1 PASS：目標已完整達成，且未發現超出目標的變更`。
   - 若缺少必要交付、實作不符合目標或變更超出目標，Gate 1 標記為 `ISSUE_FOUND`。每項 issue 先用一句簡短且可獨立理解的描述列出，再依第 1.3 節處理。
   - 任一階段缺少必要資訊時，記錄 `BLOCKED` 和原因。
2. Gate 2 依第 2.2 節完整分析原有邏輯變動。輸出時，每項變動只用一句話概述原有行為、變更後行為和主要影響。AI 必須保留變動位置、影響對象、預期效用和可能風險，供讀者要求時展開。
   - 變動本身不是 issue，也不進入第 1.3 節的處理流程。開發者依第 2.2 節確認後，Gate 2 記錄為 `PASS`。
   - 沒有發現變動時，只輸出 `Gate 2：未發現原有邏輯變動`。開發者確認後，Gate 2 記錄為 `PASS`。
   - 若變動也暴露風險，交由 Gate 3 至 Gate 6 判斷。
3. Gate 3 至 Gate 6 用來發現問題。沒有 issue 時，只輸出 `<Gate> PASS：未發現問題`。發現 issue 時，標記為 `ISSUE_FOUND`，並逐項編號。
   - 每項 issue 先用一句可獨立理解的短描述概述問題，再依第 1.3 節說明依據、影響、解決方向和下一步行動。
   - 不得使用「可能有問題」等無法說明問題本質的描述。不得把不同問題合併成一項。
4. Gate 1 第二階段與 Gate 3 至 Gate 6 的 issue，必須依第 1.3 節處理並記錄，或依第 1.7 節人工終止。同一 Gate 的所有 issue 都有允許通過的處理結果後，才能記錄 `PASS`。若較高優先級 issue 已有允許通過的結果，其餘 issue 也可以由人工終止。任一 issue 尚未處理完畢時，Gate 維持 `ISSUE_FOUND`。其他未處理 issue 依第 3 項保留原始描述。
5. Gate 7 只記錄已執行的測試命令或範圍、結果和失敗歸屬，不重述前六個 Gate 的分析。
   - 若測試失敗由本分支引入，標記為 `ISSUE_FOUND`，並記錄測試命令和簡短結果。
   - 若測試失敗不是本分支造成，標記為 `非本分支失敗`，並記錄命令、案例和歸屬依據。Gate 可以判定為 `PASS`。
   - 若無法執行測試或無法判斷失敗歸屬，標記為 `BLOCKED`，並附上一句原因。
   - 其他尚未執行的驗證只記錄在 Review 結論中。

`BLOCKED` 和 `N/A` 都必須附上一句原因。

最終 Review 文件依序記錄以下內容：`Review 基準`、Gate 1 目標與完整性結果、Gate 2 變動、Gate 3 至 Gate 6 問題結果、Gate 7 測試結果，以及 `Review 結論`。不得另外建立內容不同的摘要。

Review 期間，AI 只能新增或修改本次唯一的 Review 文件。AI 不得修改程式碼、`devlope_guides/issue/**` 或其他文件。

每個 PR 必須在 `devlope_guides/review/` 維護一份 Review 文件。正式檔名為 `devlope_guides/review/pr-<PR 編號>-review.md`。Review 期間，AI 以目前 session 的對話保存工作狀態。AI 在形成最終結論時，再集中寫入或更新文件，不必每次互動後立即寫檔。

同一 PR 進行多輪 Review 時，必須沿用原文件，並更新比較 commit、Gate 狀態和最終結論。Issue 的保留或移除依第 1.3 節處理。

尚未取得 PR 編號時，暫用 `devlope_guides/review/pending-<branch slug>-review.md`。取得 PR 編號後，沿用同一份內容並重新命名。不得建立第二份文件。既有歷史 Review 文件不必回溯改名。

### 1.7 分析完成、Issue 優先級與人工終止

本節規定分析完成條件、issue 揭露順序和人工終止範圍。人工終止只停止輸出和處理終止點以下的 issue，不得縮小第二章和第三章要求的分析範圍。

AI 必須先完成分析並排序，再提出 issue。開發者必須先看到目前未處理問題中優先級最高的 issue。本節適用於 Gate Review 和 PR Reviewer 全域審核，但只處理 AI 靜態分析發現的 issue。不得人工終止 Gate 7 確認由本分支引入的測試失敗，也不得人工終止 `BLOCKED`。

1. `必要分析範圍與排序`
   - Gate Review 必須完成目前 Gate 的全部分析。PR Reviewer 全域審核必須檢查完整 base-to-head diff、Gate 1 至 Gate 6 的必分析項目，以及所有適用的選擇分析項目。
   - AI 必須依 issue 的影響程度、發生可能性和影響範圍排序。若多項 issue 有相同根因，或可以用同一項修正處理，AI 必須合併它們。不得拆分問題來增加 issue 數量。
   - 影響實作目標、正確性、安全性、資料一致性、相容性或必要驗證的 issue 優先處理。風格偏好、理論上的改善或沒有具體影響的內容，不得列為高優先級 issue。
2. `完成宣告與 Issue 揭露`
   - AI 必須先完成必要分析和排序，再於首次輸出 issue 前宣告「分析與排序已完成」。AI 必須依優先級由高至低揭露 issue。每次提出 issue 時，AI 必須確認已揭露所有優先級更高的已知問題。
   - 若 AI 尚未完成分析、缺少判斷資訊或無法確定優先順序，不得宣告分析完成，也不得接受人工終止。Gate Review 必須判定為 `BLOCKED`。PR Reviewer 必須在 review summary 說明尚未完成的範圍。
   - 完成宣告只表示 AI 已依目前的 base、head、規格、程式碼和可取得證據完成分析。這不表示沒有其他問題。
3. `重大遺漏與補充揭露`
   - 若未處理的問題會實質影響分支目標、正確性、安全性、資料一致性、相容性、可維護性或必要驗證，該問題就是 blocking issue。Gate Review 遇到 blocking issue 不得通過。PR Reviewer 必須依第 1.3 節使用 `REQUEST_CHANGES`。
   - 首次輸出後，若 AI 發現遺漏的 blocking issue，或發現優先級更高的 issue，這就是重大遺漏。AI 必須立即補充判斷依據、影響範圍和優先級，重新排列尚未處理的 issue，並更新相關 Gate 狀態或 review summary。
   - 即使 base、head 或既有證據沒有變，AI 仍必須更正重大遺漏。AI 宣告分析完成後，若 base、head、規格、程式碼和其他證據都沒有變，則不得以一般 finding 名義新增非重大遺漏。新增 finding 導致 Gate 狀態改變，本身不足以將同級或較低優先級的非 blocking issue 判定為重大遺漏。
4. `人工終止`
   - AI 宣告分析與排序完成後，開發者可以要求終止目前 Gate 或 PR Reviewer 後續 issue 的輸出和處理。開發者可基於以下理由提出要求：issue 過度細碎、修正效益不足，或不值得繼續展開。
   - 人工終止涵蓋觸發終止的 issue，以及所有尚未輸出或尚未處理、且優先級不高於該 issue 的 finding。這些 finding 不必逐項完成開發者論證。
   - 終止點以上的高優先級 issue 必須已有明確結果，例如已修正、不採納或延後處理。若這些 issue 尚未形成允許通過的結果，或 Review 為 `BLOCKED`，不得以人工終止取得 `PASS` 或 `APPROVE`。
   - 收到終止要求後，AI 必須用一句話說明終止範圍和主要殘餘風險。AI 不得重複相同論點來延長 Review。人工終止表示開發者接受不再展開涵蓋範圍內的 finding，不表示 AI 判定這些 finding 不成立。
   - 若 AI 發現第 3 項定義的重大遺漏，受影響的排序、人工終止範圍和 Review 結論立即失效。若重大遺漏的優先級高於原終止點，或該遺漏是 blocking issue，原終止不涵蓋該問題。AI 必須補充分析並重新判定。
   - 原終止點以下且不影響合併判斷的 finding，仍維持原終止結果。AI 不得藉重大遺漏持續追加已終止的低優先級問題。
5. `結果與紀錄`
   - Gate Review 完成人工終止後，將觸發終止的 issue 記錄為「人工終止」，不再視為未處理。Gate 記錄為 `PASS`，並附註「人工終止低優先級 issue」。
   - 最終 Review 文件必須保留觸發終止 issue 的原始描述、終止原因、涵蓋範圍和主要殘餘風險。不得逐項記錄尚未展開的低優先級 finding。
   - PR Reviewer 完成人工終止後，必須在 PR 保留觸發終止的 issue。不得逐項標記尚未展開的低優先級 finding。review summary 必須記錄終止原因、涵蓋範圍和主要殘餘風險。
   - 人工終止只完成靜態 issue 的處理。Reviewer 仍須依第 1.3 節完成 Gate 7，才能決定是否使用 `APPROVE`。
   - 若 base、head、規格、程式碼或其他判斷證據改變，原有分析、排序和人工終止範圍失效。AI 必須重新分析和排序，才能提出新 issue 或再次接受人工終止。

## 二、必分析項目

必分析項目是所有分支的最低 Review 基準。Gate Review 以這些項目構成七個 Gate。

PR Reviewer 全域審核先依 Gate 1 至 Gate 6 完成靜態分析和 issue 處理，再依 Gate 7 執行本機單元測試。PR Reviewer 可以自行安排前六個 Gate 的分析順序，不必要求開發者確認，不必設定 Gate 狀態或輸出 `N/A`，也不必逐 Gate 輸出。

PR Reviewer 即使整合輸出或審查小型分支，也必須完成 Gate 1 至 Gate 6 的每項分析。Reviewer 必須依第 1.3 節為每項 issue 標記主要 Gate。`N/A` 只適用於 Gate Review，且只可用於各 Gate 明確允許的情況。

### 2.1 Gate 1：分支實作目標、完整性與範圍

此 Gate 先建立經開發者確認的目標，再用目標檢查實作是否完整，以及變更是否超出範圍。

若 AI 和開發者對目標的理解不同，AI 必須重新分析。理解差異本身不是 issue。只有第二階段發現實作缺漏、不一致或超出範圍時，才標記 `ISSUE_FOUND`，並依第 1.3 節處理。

1. `第一階段：目標來源與輸出`
   - 完整 base-to-head diff 是必要依據。AI 必須同時檢查目標分支中與變更相關的規格、設計、API 契約、JSON 資料格式或其他資料格式變更、操作文件、呼叫鏈、資料流、狀態轉換、外部副作用及測試設計。
   - 具有相關設計書或規格時，必須結合文件與程式碼變動判斷；沒有相關文件時，則從 diff、呼叫鏈與測試設計推導。
   - 若文件和程式碼呈現的目標不同，AI 必須說明差異，並請開發者校準意圖。AI 不得將理解差異直接判定為 issue，也不得只採用文件或程式碼其中一方的說法。若資訊仍不足以確定目標，判定為 `BLOCKED`。
   - AI 必須將分支濃縮為一個或少數具體目標。單一目標不得超過 100 字；只有分支確實包含可獨立驗證的子目標時，才能拆成最多三項，每項不得超過 100 字且總長不得超過 300 字。
   - 每項目標都必須說明要解決的問題、預期行為與完成條件，不得只列修改手段或檔案清單。
   - 若目標難以收斂或證據不足，AI 必須在目標清單後用一句話說明。若缺少必要資訊，無法形成具體目標，判定為 `BLOCKED`。
2. `第一階段：開發者確認`
   - AI 整理目標後，必須請開發者確認目標是否符合其意圖。只有 AI 已提出具體目標，且開發者確認一致，第一階段才算完成。
   - 開發者確認只用來校準意圖，不代表實作已完成。若雙方理解不同，AI 必須依開發者的說明重新比對文件和 diff。AI 不得只為符合開發者的說法而改寫目標。若重新分析後仍無法取得一致理解，判定為 `BLOCKED`。
   - 開發者確認目標只代表第一階段完成。Gate 1 尚未通過。AI 必須繼續第二階段。
3. `第二階段：實作完整性與範圍判斷`
   - AI 必須逐項將已確認目標和完成條件與實際程式碼、文件、測試設計、呼叫鏈、資料流、狀態轉換和外部副作用比較。AI 必須確認所有必要交付都已完成。
   - AI 必須確認每項變更都符合已確認目標，或是完成目標所需的配套。變更中不得混入無關重構、額外功能或未說明的副作用。
   - 若文件、規格或測試宣稱某行為已完成，但程式碼沒有支援，或實作不符合已確認目標，標記為 `ISSUE_FOUND`。
   - 缺少必要交付、只完成部分目標或有超出目標的變更時，逐項標記為 `ISSUE_FOUND`。若資訊不足以判定，標記為 `BLOCKED`。
4. `第二階段：Gate 結果`
   - 沒有發現實作缺漏、不一致或超出目標的變更時，Gate 1 判定為 `PASS`。
   - 發現 issue 時，依 1.3 至 1.7 節完成歸屬判斷、處理引導、修正重跑、開發者論證或人工終止，以及結果保存。

### 2.2 Gate 2：原有業務邏輯變更

此 Gate 找出目前分支對原有邏輯造成的直接或間接變動。AI 必須讓開發者了解變動範圍、預期效用和風險。即使分支只包含重構或技術調整，AI 也必須檢查實際行為是否改變。

Gate 2 必須依下列三項完成分析：

1. `分析範圍`
   - AI 必須檢查業務邏輯、資料寫入、顯示、元件組裝和條件判斷。AI 也必須檢查相關輸入、輸出、狀態轉換、錯誤處理和外部副作用。
   - 分析必須比較修改前後的實際行為，不得只根據檔名、函式名稱或程式碼結構判斷。
2. `變動列舉`
   - AI 必須列出所有已識別的原有邏輯變動。完整分析必須說明變動位置、原有行為、變更後行為、影響對象、預期效用和可能風險。實際輸出依第 1.6 節濃縮為一句短描述。
   - 若未發現舊有邏輯變動，AI 仍須完成主要路徑與判斷依據的分析，但輸出只記錄未發現變動。
3. `開發者確認`
   - 開發者必須確認已知悉 AI 列出的所有可能變動。開發者也必須確認變動範圍和數量受到控制，並已了解每項變動的效用和風險。
   - 開發者認為列舉內容有遺漏或判斷不一致時，AI 必須依補充說明重新檢查相關程式碼與文件，再更新變動清單。

### 2.3 Gate 3：原有 Runtime 潛在錯誤風險

此 Gate 檢查既有 runtime 路徑的回歸風險。AI 必須確認本次變更不會讓原本可運作的流程出現新的失敗條件。

Gate 3 檢查變更對既有行為的影響。Gate 4 檢查新增流程本身的錯誤風險。

通過此 Gate 必須以靜態分析確認：

1. 既有呼叫鏈、模組匯入、服務初始化、設定載入、API 路由掛載與介面實作沒有因變更而中斷。
2. 既有成功、失敗、重試、timeout、取消與補償路徑沒有新增未處理的分支。
3. 不會新增可預見的未捕捉例外、`null`／`undefined` 存取錯誤、未處理的 Promise rejection、資源未釋放或錯誤吞沒風險；如有 worker 或背景工作，也須檢查其生命週期與錯誤處理。
4. 對既有 API、事件、資料格式或部署順序的相容性影響已被識別並處理。

純文件變更且不影響程式執行方式時，此 Gate 可以判定為 `N/A`，並依 1.6 節只附上一句原因。

### 2.4 Gate 4：新增錯誤風險

此 Gate 檢查本次新增的程式、流程、狀態和依賴是否引入新的錯誤模式。AI 必須從新增入口追蹤到輸出和失敗處理，並確認系統能控制、回傳、記錄或補償錯誤。

通過此 Gate 必須以靜態分析確認：

1. 新增輸入與前置條件具有完整驗證，不會讓非法或不完整資料進入核心流程。
2. 新增分支、狀態、外部呼叫與 Promise／非同步流程都具有明確的失敗行為。
3. 後端錯誤依專案規範使用 `AppError` 與 `try-catch`，錯誤映射、HTTP 狀態碼、回傳結果、重試、補償與日誌符合 API 規格；前端錯誤狀態則須符合使用者可觀察的流程。
4. 新增錯誤風險已有對應防護，沒有未揭露且可能影響正確性或可用性的風險。

分支沒有新增程式、流程、狀態或依賴時，此 Gate 可以判定為 `N/A`，並依 1.6 節只附上一句原因。

### 2.5 Gate 5：架構、封裝與依賴

此 Gate 確認實作符合 `AGENTS.md` 的專案架構政策。元件邊界必須清楚，型別、介面和呼叫方向不得洩漏不應跨層的知識。AI 必須檢查元件放置位置和依賴是否必要，即使程式可以編譯也一樣。

通過此 Gate 必須確認：

1. 後端業務邏輯與 TypeScript 介面放在 `src/domains/`，HTTP 傳輸與 payload 轉發放在 `src/server/routes/`；前端畫面與元件放在 `web/`，且沒有新增違反專案路徑分界的依賴。
2. 業務規則、流程協調、傳輸層與 UI 責任放在正確層級，沒有把核心業務邏輯放進 API route，也沒有將後端 Bun／Node API 引入前端程式碼。
3. 元件沒有洩漏不必要的 HTTP request／response 細節、前端元件型別或其他基礎設施細節到不應依賴它們的層級；前後端透過既有 API 契約交換資料。
4. 介面與封裝維持必要且最小的依賴，沒有過度抽象、循環依賴、過大介面或不必要耦合。

純文件變更且不調整架構規格時，此 Gate 可以判定為 `N/A`，並依 1.6 節只附上一句原因。

### 2.6 Gate 6：重要資料持久化靜態安全性

此 Gate 適用於會影響資產或業務事實的持久化變更，例如訂閱、出款和入款狀態。

本專案使用 JSON 檔案保存資料。AI 必須追蹤 `data/*.json` 的讀取、寫入、轉換、重置和失敗處理。不得假設專案使用資料庫或資料庫交易。

Gate 結論只表示靜態分析沒有發現未處理的風險。不得宣稱 runtime 行為已證明資料絕對安全。

通過此 Gate 必須確認：

1. 重要資料的寫入來源、資料轉換、更新條件與最終狀態可完整追蹤。
2. JSON 檔案更新、暫存檔或替換流程的原子性、併發寫入與失敗復原符合業務不變式；若目前實作沒有提供相關保護，須評估其實際影響。
3. 重複請求、重試、重複執行或非同步操作不會造成重複記錄、狀態倒退或部分寫入。
4. 狀態轉換、必要欄位、唯一性檢查、`null`／缺欄位處理與讀寫一致性沒有可由靜態分析識別的缺口。
5. 持久化資料與 Domain、API 及 UI 間的轉換符合既有型別、驗證器與 API 契約，不得在本指南另行假設未由專案規格定義的金額格式。

若分支完全不涉及重要資料的建立、修改、刪除或寫入決策，此 Gate 可以判定為 `N/A`。依第 1.6 節附上一句原因。

### 2.7 Gate 7：本機單元測試

Gate 7 是唯一會執行程式碼的 Review Gate。進入條件依第 1.2 節辦理。

通過此 Gate 必須確認：

1. 依變更範圍和 `AGENTS.md` 的「Build, Test, and Verification Commands」執行對應的本機單元測試。若只執行特定測試檔，必須依 `AGENTS.md` 和現有 test script 保留該側的 preload 與環境設定，再依變更風險決定是否擴大到整側測試。
2. 使用 `AGENTS.md` 規定的專案測試工具、setup、隔離伺服器與 fixture 規則。不得將前端 Happy DOM 設定套用到後端測試，也不得寫入或覆蓋原始 JSON 資料檔。
3. Review 紀錄只列出實際命令或測試範圍、結果及失敗歸屬，不得貼上完整輸出。
4. 測試失敗時，AI 必須比較 base 和目前分支的相同測試結果或相關程式證據，並判斷失敗是否由本分支引入。
   - 若本分支引入失敗，標記為 `ISSUE_FOUND`，並記錄測試命令和簡短結果。
   - 若失敗不是本分支造成，標記為 `非本分支失敗`。記錄測試命令、案例和歸屬依據後，Gate 可以判定為 `PASS`。
   - 若無法判斷失敗歸屬，標記為 `BLOCKED`。
5. 缺少必要環境或相依資源而無法執行時，必須判定為 `BLOCKED`，不得視為通過。

Gate 7 只執行本機單元測試。不得擴大到需要外部環境的整合測試或 E2E。若分支需要整合測試、E2E 或部署驗證，必須在 Review 結論中另列為後續驗證。

純文件變更若沒有對應的單元測試，此 Gate 可以判定為 `N/A`。依第 1.6 節附上一句原因。

## 三、選擇分析項目

選擇分析項目補足特定分支的風險。AI 必須依完整 diff 判斷哪些項目適用。符合適用條件的項目就是本次 Review 的必要分析內容。

Gate Review 將適用項目併入最相關的 Gate 3 至 Gate 6，不改變 Gate 1 至 Gate 7 的順序。PR Reviewer 全域審核可以整合不同項目的分析，但必須將 issue 歸入最相關的 Gate 3 至 Gate 6。Reviewer 必須依第 1.3 節標記主要 Gate，再將 issue 標記於 PR。

### 3.1 效能影響

此項適用於查詢、批次處理、報表、大量 I/O 或高頻流程。分析資料量成長、查詢次數、記憶體、CPU、網路 I/O、鎖定範圍和延遲風險。

### 3.2 安全性與權限

此項適用於登入、認證、授權、敏感資料、管理後台或商戶隔離。分析權限邊界、資料隔離、輸入驗證、secret 處理、敏感資訊遮罩和未授權存取風險。

### 3.3 資料一致性、交易與併發

此項適用於跨流程、非同步事件或多次檔案操作造成的資料一致性風險，例如狀態機、重複請求、出入金和補償流程。

此項延伸 Gate 6。分析操作順序、競態條件、冪等、重試、亂序和部分失敗。只有程式實際使用資料庫交易或外部服務時，才檢查相關交易或跨服務邊界。

### 3.4 JSON 資料格式與檔案 I/O 成本

此項適用於 `data/*.json` 格式、讀寫流程或大量資料處理變更。分析既有資料相容性、缺欄位與型別驗證、檔案讀寫次數、資料量成長、併發寫入、檔案替換和失敗復原風險。

若未來新增其他持久化技術，依實際使用的 schema、查詢和回滾機制補充分析。

### 3.5 API 契約與前後端同步

此項適用於 OpenAPI、SDK、handler、前端串接或對外回應欄位變更。分析契約先行、產碼一致性、相容性、錯誤映射、路由掛載和前後端資料語意。

### 3.6 UI 與使用流程

此項適用於頁面互動、操作流程、表單或錯誤提示變更。分析 loading、empty、error、success、權限狀態、重複操作、回饋一致性和可恢復性。

### 3.7 日誌、追蹤與可觀測性

此項適用於 logging、trace、監控事件、錯誤定位或稽核需求。分析排錯所需的最少資訊、結構化欄位、敏感資訊遮罩、trace 關聯、錯誤標記和告警可用性。

### 3.8 部署、相容性與回滾風險

此項適用於設定調整、相依版本升級、資料格式變更、部署流程或跨版本相容性變更。分析 rollout 順序、向前和向後相容、設定預設值、舊版本共存、失敗回滾和資料復原。
